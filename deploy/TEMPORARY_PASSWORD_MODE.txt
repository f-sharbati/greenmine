The owner authorized production access with email and password while SMTP is pending.
GREENMINE_AUTH_MODE=password explicitly enables this temporary behavior. The image default remains email_otp; missing/failed mail never selects password mode.

The overlay changes authentication entry points and UI only. Prediction, reference data, CSV algorithms, original Python engine and mail-delivery code remain the supplied versions. The original archive manifest is preserved and password-mode-overlay.json lists the authorized exceptions.

Password-mode signup still validates CAPTCHA and password confirmation, uses PBKDF2-HMAC-SHA-256 (600000 iterations), starts with empty plant/history, and creates an active account/session. Inactive accounts remain inactive. Existing IDs, data, sessions and passwords are preserved; legacy password hashes upgrade after a successful password check. Email recovery requires configured SMTP.

Deployment helper:
  python3 /opt/greenmine/ops/auth-20261031/release-ops.py --promote --auth-mode password
This choice skips SMTP preflight only because the operator explicitly selected the authorized password mode. It preserves/freeze-backs-up the current database and service configuration before replacing the app.

After fresh Gmail SMTP is supplied:
  python3 /opt/greenmine/ops/auth-20261031/release-ops.py --bootstrap-mail /opt/greenmine/config/mail-fresh.env
  python3 /opt/greenmine/ops/auth-20261031/release-ops.py --promote --auth-mode email_otp
The second command requires real SMTP authentication before changing the mode. Existing sessions/data remain. Complete live OTP delivery and recovery acceptance; do not describe email as verified before that. There is no scheduled date-based change.

The previous binary cannot verify upgraded PBKDF2 hashes. Use the guarded rollback procedure only before authentication/business data changes, otherwise preserve current data and use a forward fix. Never blindly restore a stale database backup.
